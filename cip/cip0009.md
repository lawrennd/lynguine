# CIP-0009: Config-driven remote materialise before local read

> **Note**: CIPs describe HOW to achieve requirements (WHAT).
> Use `related_requirements` to link to the requirements this CIP implements.

## Summary

Wire lynguine's existing download helpers into `CustomDataFrame.from_flow()`
so that an interface item can declare an optional **`remote:`** block.
When `remote:` is present, the access stage **materialises** (or confirms)
a local cache of the remote artefact, then the existing `read_data` path
reads it by `type:`. When `remote:` is absent, behaviour is unchanged.

This is the missing general “download / refresh a local copy, then read”
stage. It complements [CIP-0019](./cip0019.md) live readers (Trello, IMAP,
`type: gdocs`, …): those hit the network at read time; this CIP fills a
**file on disk** first. External syncers (offlineimap, mbsync) remain
valid for Maildir — they are the same pattern owned outside lynguine.

Implements [REQ-0009](../requirements/req0009_config-driven-remote-access.md);
closes the design gap in [lynguine#20](https://github.com/lawrennd/lynguine/issues/20)
(from referia#9). **Next implementation work after CIP-0019 plugins.**

**Which requirements does this CIP address?** REQ-0009 (primary),
REQ-0002 (predictable, explicit flow), REQ-0004 (credentials for private
sources), REQ-000A (cache paths stay in the jail).

## Motivation

referia#9 asked for configuration that triggers download before read
(URL, GitHub, authorise). Helpers already exist
(`FileDownloader`, `GitDownloader` in `lynguine/access/download.py`) but
`from_flow` never calls them. Operators copy files by hand or run
scripts outside the documented data path — that violates flow-based
processing.

CIP-0019 then shipped **live** tabular plugins. That made a second
pattern clear:

| Pattern | Owns credentials? | Local artefact? | Where |
|---------|-------------------|-----------------|--------|
| Live reader | Yes (CIP-0005 via `credential:`) | No | CIP-0019 `type: trello` / `imap` / `gdocs` |
| Materialise then read | Optional on `remote.credential` | Yes — file/tree under cache | **This CIP** (`remote:` + local `type:`) |
| External syncer | Outside lynguine | Yes — e.g. `~/Maildir` | Operator (offlineimap); lynguine only reads (`type: maildir` / `mu`) |

Google Sheets stays a live reader (`type: gsheet`), not a `remote:`
fetch. Docs **can** later export to disk and then use CIP-0013
`markdown` (or a frozen catalogue YAML) — that is a `remote.type` once
the result is files, not a second live-reader shape. IMAP sync into
Maildir stays outside lynguine unless a separate sync package is
deliberately owned later.

CIP-0007 already treats `access/download.py` as a lynguine primitive.
This CIP makes that primitive reachable from interface configuration.

## Detailed Description

### Design principle

Materialise is part of **access**, not construction and not assess.
`from_flow` already walks `input` / `output` / `cache` items and calls
`access.io.read_data`. Insert one explicit step *before* that call: if
the item has `remote:`, materialise a local file (or confirm the cache),
then read as today.

We do **not** infer a download from a `filename` that looks like a URL.

### Naming: `remote:` not `source:`

[CIP-000F](./cip000F.md) already uses `source:` for **directory discovery
entries** (`directory` / `glob` / `recursive`). Reusing `source:` for
URL/Git fetch collided with that key.

This CIP uses **`remote:`** for fetch-then-read metadata. CIP-000F
`source:` lists stay as they are. Orthogonal composition:

```yaml
input:
  type: yaml_directory
  remote:
    type: github
    url: https://github.com/example/allocations.git
    refresh: false
  directory: .lynguine-cache/alloc-repo
  source:
    - directory: .
      glob: "**/_referia.yml"
      recursive: true
```

Flow order: materialise `remote:` → then directory `source:` discovery
and `type:` read under the confined cache root ([CIP-000A](./cip000A.md)).

### Configuration shape

Keep fetch metadata on the same item as the local reader. One data
item, two access sub-steps.

**URL fetch then YAML read:**

```yaml
input:
  type: yaml
  filename: candidates.yml
  directory: .lynguine-cache/candidates
  index: Name
  remote:
    type: url
    url: https://example.org/lists/candidates.yml
    license: "See source site terms."
    refresh: false
```

**Git clone/pull then CSV read:**

```yaml
input:
  type: csv
  filename: data/candidates.csv
  directory: .lynguine-cache/alloc-repo
  index: Name
  remote:
    type: github
    url: https://github.com/example/allocations.git
    refresh: false
```

`filename` / `directory` remain the local path `read_data` uses.
`remote` describes how that path is filled. For Git, `filename` is
relative to the clone directory.

**Google Sheets** stays a reader, not a `remote` type:

```yaml
input:
  type: gsheet
  key: "spreadsheet-id"
  sheet: "Candidates"
  index: Name
```

### Relation to CIP-0019 (live vs materialise)

```yaml
# This CIP — file appears on disk, then type: yaml
input:
  type: yaml
  filename: candidates.yml
  directory: .lynguine-cache/candidates
  remote:
    type: url
    url: https://example.org/candidates.yml

# CIP-0019 — no file; type is the live store
input:
  type: trello
  board: "review-inbox"
  index: id
  credential: my_trello
```

Do **not** add `remote.type: trello` or `remote.type: imap`. Live APIs
are readers. A plugin may later offer an **optional snapshot** that
writes files under a cache directory and then uses this CIP’s hook
(documented, still explicit `remote:` + local `type:`). That is not the
default for Trello/IMAP/`gdocs`.

Maildir: offlineimap remains an **external** materialiser. lynguine
reads `type: maildir` / `type: mu` with no credential. A future
`lynguine-offlineimap` (or similar) would be a sync package, not a
widening of `remote.type` in v1 — unless its output is literally “files
under `directory`” and registers as a `remote.type`.

### `remote.type` in the first delivery

| `remote.type` | Action | Local path |
|---|---|---|
| `url` | HTTP(S) GET via existing `_download_url` | `directory` / `filename` |
| `github` | `GitDownloader` clone or pull | clone root is `directory`; read `filename` inside it |

Deferred (same hook, later CIPs or plugin registration):

- **SQL / Trello / IMAP / live gdocs** — CIP-0019 readers, not `remote.type`.
- **Docs / Drive export to disk** — when the result is files (markdown,
  HTML, YAML catalogue dump), add a `remote.type` (core or plugin) that
  materialises under `directory`, then CIP-0013 / local `type:` reads.
- **S3, Dropbox, …** — same rule: only when the result is a **file on
  disk**.
- Pluggable `register_remote_type` mirroring CIP-0019 is attractive once
  `url` / `github` prove the `from_flow` wiring; not required for v1.

### Authorization (no new `authorize.py`)

1. **Licence / terms prompt** — keep `_authorize_download()` (or a
   small extraction) driven from `remote.license` / `remote.details`.
   Honour `overide_manual_authorize` for non-interactive runs.
2. **Secrets** — private Git remotes and authenticated HTTP use
   CIP-0005. Optional `remote.credential` names a key. Do not put
   tokens in YAML. Prefer aligning with CIP-0019’s
   `authorize_access` + `get_credential` path where a known
   `credential_type` applies; v1 may start with a thin bind and
   document the type.

### Flow algorithm

In `CustomDataFrame.from_flow`, for each valid data item, before
`read_data` / `data_exists`:

1. If `remote:` is absent, current behaviour.
2. If `remote:` is present, validate `remote.type` against the registry
   (`url`, `github` in v1).
3. Resolve the local destination from `directory` + `filename` under
   CIP-000A allowed roots.
4. If the local file (or Git repo) exists and `remote.refresh` is not
   true, skip fetch.
5. Otherwise run the matching downloader, then continue to `read_data`.

`data_exists` for remoted items means “local cache present or fetch
succeeded”, not “remote HEAD is 200”. After a failed fetch, raise
`ValueError` naming `remote.type`, URL, and the underlying error. Do
not fall through to an empty **input** frame.

### Why not a second interface file?

A URL→file flow followed by a second read flow splits one data item and
hides the access stage. Users may still compose two flows. The primary
design keeps `remote:` on the item that is read.

### Relationship to other CIPs

- **CIP-0005 (Closed)**: credential store for private remotes.
- **CIP-0007 (Proposed)**: download stays in lynguine; this CIP uses it.
- **CIP-0008 (Proposed)**: fetch remains an access-stage call in-process.
- **CIP-000A (In Progress / path jail)**: cache paths must stay inside
  `allowed_roots`.
- **CIP-000F (Closed)**: directory `source:` lists; naming resolved via
  `remote:`.
- **CIP-0013**: after materialise, document readers consume local paths
  or bytes.
- **CIP-0019 (Implemented)**: live tabular plugins; points here for
  fetch-then-read. **This CIP is the next core access work.**

### Security constraints

- Fetch only URLs and Git remotes written in configuration, never
  values from the data frame.
- Write downloaded files only under the resolved `directory` (CIP-000A).
- Do not log credential values.

## Implementation Plan

1. **Schema and validation**
   - Document `remote` keys: `type`, `url`, optional `license`,
     `details`, `citation`, `refresh`, `credential`.
   - Reject unknown `remote.type` clearly.
   - Reject configs that still use the old proposed key name `source:`
     *as a remote mapping* with a migration error pointing at `remote:`.

2. **Access-stage helper**
   - Add `lynguine.access.download.materialise(item, interface)` that
     dispatches `url` / `github` and returns the local path.
   - Reuse `FileDownloader` and `GitDownloader`; keep them working for
     `clone_or_pull.py`.

3. **Wire `from_flow`**
   - Call materialise before `data_exists` / `read_data` when `remote`
     is set.
   - Leave gsheet, CIP-0019 plugins, and local-only items on the
     current path.

4. **Tests**
   - Dispatch, skip-if-cached, `refresh: true`, unknown type, HTTP/Git
     error, no implicit URL-from-filename.
   - Integration: mocked fetch then `read_data` of the cached file.
   - Assert CIP-000F directory `source:` lists still parse.

5. **Documentation**
   - README / Access: `remote:` on an `input` item; contrast with
     CIP-0019 live `type:`.
   - Note gsheet remains a reader; SQL/Trello/IMAP stay CIP-0019.
   - Note Maildir sync stays external unless a later `remote.type`.

## Backward Compatibility

- Items without `remote:` are unchanged.
- CIP-000F `source:` directory lists are unchanged.
- `FileDownloader` / `GitDownloader` public methods stay for existing
  callers.
- `type: gsheet` and CIP-0019 plugins are unchanged.
- No referia change unless a config opts into `remote:`.

## Testing Strategy

- Mock network and git; no live internet in CI.
- Assert `from_flow` calls materialise only when `remote:` is present.
- Assert cached files are not re-fetched unless `refresh: true`.
- Assert failures surface as `ValueError` and do not create empty
  input frames.
- Extend `lynguine/tests/test_access_download.py`; add a `from_flow`
  test in the data-flow suite.
