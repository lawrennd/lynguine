# CIP-0009: Config-driven remote access in the data flow

## Summary

Wire lynguine's existing download helpers into `CustomDataFrame.from_flow()` so that an interface item can declare an optional `source` block. When `source` is present, the access stage fetches (or refreshes a local cache of) the remote file or Git repository, then the existing `read_data` path reads it by `type`. When `source` is absent, behaviour is unchanged.

This CIP implements [REQ-0009](../requirements/req0009_config-driven-remote-access.md) and closes the design gap in [lynguine#20](https://github.com/lawrennd/lynguine/issues/20) (transferred from referia#9).

**Which requirements does this CIP address?** REQ-0009 (primary), REQ-0002 (predictable, explicit flow), REQ-0004 (credentials for private sources).

## Motivation

referia#9 asked for a configuration form under `input` / `output` that triggers download before read:

```yaml
input:
  source:
    type: url
  type: yaml
```

plus GitHub, SQL, Google Sheets, and an authorise step. The original text pointed at `ndlpy/access/download.py` and a sibling `authorize.py`.

What exists today:

| Capability | Status | Used from `from_flow`? |
|---|---|---|
| `FileDownloader` / URL fetch | Implemented in `lynguine/access/download.py` | No (tests and `clone_or_pull.py` only) |
| `GitDownloader` clone/pull | Implemented | No |
| Licence / prompt authorise | `_authorize_download()` | No |
| Google Sheets read/write | `type: gsheet` in `io.py` | Yes |
| Encrypted credentials | CIP-0005 (Closed) | Yes, for gsheet |

The gap is not another downloader. The gap is an explicit access-stage step in the flow: configuration names a remote source, the flow fetches, then the flow reads. Without that wiring, operators copy files by hand or call helpers outside the documented data path, which violates flow-based processing.

CIP-0007 (Proposed) already treats `access/download.py` as a lynguine storage primitive. This CIP makes that primitive reachable from interface configuration. It does not wait on the vongole split.

## Detailed Description

### Design principle

Download is part of **access**, not of construction and not of assess. `from_flow` already walks `input` / `output` / `cache` items and calls `access.io.read_data`. We insert one explicit step *before* that call: if the item has `source`, materialise a local file (or confirm the cache), then read as today.

We do **not** infer a download from a `filename` that looks like a URL. That would be implicit behaviour in the infrastructure layer.

### Configuration shape

Keep fetch metadata on the same item as the local reader. One data item, two stages.

**URL fetch then YAML read:**

```yaml
input:
  type: yaml
  filename: candidates.yml
  directory: .lynguine-cache/candidates
  index: Name
  source:
    type: url
    url: https://example.org/lists/candidates.yml
    license: "See source site terms."
    refresh: false
```

**Git clone/pull then CSV read:**

```yaml
input:
  type: csv
  filename: data/candidates.csv
  directory: .lynguine-cache/alloc-repo
  index: Name
  source:
    type: github
    url: https://github.com/example/allocations.git
    refresh: false
```

`filename` / `directory` remain the local path `read_data` uses. `source` describes how that path is filled. For Git, `filename` is relative to the clone directory.

**Google Sheets** stays a reader, not a `source` type:

```yaml
input:
  type: gsheet
  key: "spreadsheet-id"
  sheet: "Candidates"
  index: Name
```

Sheets are not files on disk. Forcing them through `source` + local YAML would invent a cache format we do not need. Document this as already done; do not wrap gsheet in `source`.

### Source types in the first delivery

| `source.type` | Action | Local path |
|---|---|---|
| `url` | HTTP(S) GET via existing `_download_url` | `directory` / `filename` |
| `github` | `GitDownloader` clone or pull | clone root is `directory`; read `filename` inside it |

Deferred (not in this CIP):

- **SQL** — a live query is a new reader (`type: sql`), not a file fetch. Track as a follow-on requirement if needed.
- Other hosts (S3, Dropbox, and so on) — add `source.type` values later using the same hook.

### Authorization (no new `authorize.py`)

The original issue suggested `ndlpy/access/authorize.py` beside `download.py`. We do not add that module.

1. **Licence / terms prompt** — keep `_authorize_download()` (or a small extraction of it) and drive it from `source.license` / `source.details`. Honour existing `overide_manual_authorize` for non-interactive runs.
2. **Secrets** — private Git remotes and authenticated HTTP use CIP-0005 credentials. The flow requests a named credential explicitly (`source.credential` optional key). We do not read tokens from the interface YAML.

Interactive prompts are allowed at flow time because this is access, not construction. For server/web callers, `overide_manual_authorize: true` plus a pre-agreed licence field is the non-interactive path.

### Flow algorithm

In `CustomDataFrame.from_flow`, for each valid data item, before `read_data` / `data_exists`:

1. If `source` is absent, current behaviour.
2. If `source` is present, validate `source.type` against the registry (`url`, `github`).
3. Resolve the local destination from `directory` + `filename` (and `base_directory` as today).
4. If the local file (or Git repo) exists and `source.refresh` is not true, skip fetch.
5. Otherwise run the matching downloader, then continue to `read_data`.

`data_exists` for sourced items means "local cache present or fetch succeeded", not "remote HEAD is 200". After a failed fetch, raise `ValueError` naming `source.type`, URL, and the underlying error. Do not fall through to creating an empty output frame for **input** items.

### Why not a second interface file?

The original issue offered an alternative: one interface whose input is the URL and whose output is the local file, then a second interface that reads that file. That splits one data item across two flows and hides the access stage from the review config. Users can still compose two flows if they want. The primary design keeps `source` on the item that is read.

### Relationship to other CIPs

- **CIP-0005 (Closed)**: credential store for private sources. This CIP consumes it; it does not replace it.
- **CIP-0007 (Proposed)**: package split keeps `download.py` in lynguine. This CIP uses that primitive from the flow. Neither blocks the other. If CIP-0007 later moves download APIs, this wiring follows the public access API.
- **CIP-0008 (Proposed)**: server mode. Remote fetch remains an access-stage call inside a long-running process; no special case required in this CIP.

### Security constraints

- Fetch only URLs and Git remotes written in configuration, never values from the data frame.
- Write downloaded files only under the resolved `directory` (no path escape via `filename`).
- Do not log credential values. CIP-0005 sanitisation already covers this if we go through the credential controller.

## Implementation Plan

1. **Schema and validation**
   - Document `source` keys: `type`, `url`, optional `license`, `details`, `citation`, `refresh`, `credential`.
   - Reject unknown `source.type` with a clear error.

2. **Access-stage helper**
   - Add `lynguine.access.download.materialise(item, interface)` (name can vary) that dispatches `url` / `github` and returns the local path.
   - Reuse `FileDownloader` and `GitDownloader`; adapt them to take a single item dict rather than the old `data_resources[name]` bundle where that is cleaner. Keep the old classes working for `clone_or_pull.py`.

3. **Wire `from_flow`**
   - Call materialise before `data_exists` / `read_data` when `source` is set.
   - Leave gsheet and local-only items on the current path.

4. **Tests**
   - Unit tests for dispatch, skip-if-cached, `refresh: true`, unknown type, HTTP error, Git error.
   - Integration test with a mocked `urlopen` / git, then `read_data` of the cached file.

5. **Documentation**
   - README Access section: show `source` on an `input` item.
   - Note that gsheet remains `type: gsheet`.
   - Note SQL is deferred.

## Backward Compatibility

- Items without `source` are unchanged.
- `FileDownloader` / `GitDownloader` public methods stay for existing callers (`clone_or_pull.py`, tests).
- `type: gsheet` is unchanged.
- No change to referia unless an application config opts into `source`.

## Testing Strategy

- Mock network and git; do not hit the live internet in CI.
- Assert `from_flow` calls materialise only when `source` is present.
- Assert cached files are not re-fetched unless `refresh: true`.
- Assert HTTP/Git failures surface as `ValueError` and do not create empty input frames.
- Extend `lynguine/tests/test_access_download.py`; add a `from_flow` test in the data-flow suite.
