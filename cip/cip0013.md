# CIP-0013: Pluggable document extractors — PDF/DOCX segmentation, aspects, and recognisers

## Summary

Introduce an explicit, pluggable **document extraction** layer in lynguine so flows can say: load this PDF or DOCX, recognise (or select) a layout/reference strategy, segment into units, then run optional compute for different **aspects** (body chunks, dialogue units, bibliographic references).

This CIP is the design home for work motivated by three concrete corpora:

| Corpus | Format | Aspect needed |
|--------|--------|----------------|
| [pub-dialogue](https://github.com/mlatcl/pub-dialogue) | PDF reports | Paragraph / sentence chunks → (later) concern/benefit phrases |
| [ai-dialogue-formats](https://github.com/mlatcl/ai-dialogue-formats) | DOCX transcripts | Chatbot / workshop units |
| [mlresearch](https://github.com/mlresearch) volume PDFs | Academic PDFs | End-of-paper reference lists |

**Placement (accepted):** readers, recognisers, and segmenters live in **lynguine** (`access.documents` + access-level compute). This is access-stage structuring, not assessment compute. Do **not** wait on vongole (CIP-0007); that CIP’s sketch of PDF ops under `vongole/functions/files.py` is superseded for this work.

## Motivation

### What we have today

- **lynguine** has rich tabular/directory IO (`csv`, `excel`, `yaml_directory`, `docx_directory` via pandoc→markdown) and a Compute registry, but **no PDF text reader** and no general document-segmentation model. Nested load-time compute only sees lynguine builtins (`render_liquid`, `today`) unless an app subclasses `Compute` (see CIP-0011).
- **pub-dialogue** implements a solid PyMuPDF chunker (`extract_chunks_from_pdf`) tuned to UK public-dialogue reports, with coverage-based sentence fallback. That heuristic is corpus-shaped, not general.
- **ai-dialogue-formats** parses DOCX with study-specific speaker / participant structure — again correct for that corpus, not a generic DOCX→units path.
- **mlresearch** holds hundreds of PMLR volume PDFs whose *in-paper* reference lists are not extracted by existing publishing tooling (volume BibTeX → Jekyll is a different problem).
- **CIP-0004** covers generic LLM extract/summarise — useful *after* text is structured, not a substitute for layout-aware segmentation.

### The design pressure

One PDF library (or one DOCX reader) is not enough. The **core** steps repeat (open document → obtain text/blocks → emit units), but:

1. **Paragraph / section separation** differs (single-column reports vs two-column proceedings vs transcript exports).
2. **Reference formatting** differs (author–year prose, numbered lists, DOI-heavy ACM/IEEE styles, …).
3. **Downstream aspects** differ (chunk for clustering vs dialogue unit vs citation record).

Forcing a single global heuristic will silently fail on the next corpus. We need **named strategies** plus an optional **recogniser** that proposes a strategy from document features — still explicit in the flow (user can override).

## Detailed Description

### Layered model

Keep stages explicit (access → assess → address):

```
┌─────────────────────────────────────────────────────────────┐
│ ACCESS — structure the document (lynguine)                  │
│  Reader (pdf | docx | …)                                    │
│    → raw pages / blocks / paragraphs                        │
│  Recogniser (optional)                                      │
│    → strategy id + confidence + features                    │
│  Segmenter (strategy)                                       │
│    → ordered units {unit_id, text, span, section?, …}       │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ ASPECT EXTRACTORS — project units into domain rows          │
│  body_chunks | dialogue_units | references | …              │
│  (rule-based at access; LLM optional later)                 │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ ASSESS COMPUTE — optional, registry / app functions         │
│  pub_extract_phrases, llm_extract, … (CIP-0004 / apps)      │
└─────────────────────────────────────────────────────────────┘
```

**Tenet check**: The flow names the reader, the strategy (or `auto`), and the aspect. No silent “best effort” without recording which strategy ran.

### 1. Readers (format adapters)

Thin adapters that normalise a file into a **document model**:

| Reader | Backend (initial) | Emits |
|--------|-------------------|--------|
| `pdf` | PyMuPDF (`fitz`) — proven in pub-dialogue | pages, blocks, text-layer stats |
| `docx` | `python-docx` (structured); pandoc path stays separate | paragraphs (+ styles if available) |

Readers do **not** decide research-unit boundaries. They only expose enough structure for segmenters (block bbox, font size, style name, page number) and for scan detection (words per page, extractable-text coverage).

**Home:** `lynguine.access.documents`. Optional dependency on PyMuPDF (extra), same pattern as optional Google Sheets deps — lynguine installs without PDF support; PDF reader imports fail clearly if the extra is missing.

### 2. Strategies and recognisers

Each **strategy** is a named, versioned segmenter:

```text
strategy_id: "pub_dialogue.v1" | "pmlr_twocolumn.v1" | "docx_chatbot.v1" | …
```

Responsibilities:

- Choose how to turn the document model into ordered text units.
- Declare which **aspects** it can feed (e.g. `body_chunks`, `references`).
- Expose parameters (min words, coverage threshold) as explicit config — same spirit as pub-dialogue’s `MIN_TEXT_COVERAGE`.

A **recogniser** is a pure function:

```text
features(document_model) → [{strategy_id, score, rationale}, ...]
```

Features might include: median block width, column-gap detection, presence of a “References” heading, chatbot participant headings, words-per-page (scan detector). Recognition never silently binds: the chosen strategy is written onto each row (`segment_strategy`, `recogniser_score`) so flows stay auditable.

Manual override always wins:

```yaml
args:
  strategy: pmlr_twocolumn.v1   # or auto
```

### 3. Aspects (what to extract)

Aspects are projections from segmented units (or from a dedicated pass over the same document model):

| Aspect | Output grain | Primary consumers |
|--------|--------------|-------------------|
| `body_chunks` | chunk rows (default: **exploded** — one row per unit) | pub-dialogue |
| `dialogue_units` | unit rows | ai-dialogue-formats |
| `references` | citation rows; v1 = **`ref_raw`** (+ `ref_id`, order); light parse optional later | mlresearch / bibliometrics |
| (later) `sections` | section title + body span | review UIs |

Reference extraction is itself strategy-aware: locate the references *region*, then parse entries with a **reference format strategy** (regex/heuristic first; optional LLM repair later via CIP-0004). Do not conflate region detection with entry parsing.

**Row grain (accepted):** default **explode** to one row per unit for compute ergonomics; nested list-under-file is an optional mode if a caller needs it.

**`docx_directory` (accepted):** keep the existing pandoc→markdown path for “whole doc as markdown”. Structured DOCX unitisation uses the new reader + dialogue strategies — two explicit paths, not a silent replacement.

### 4. Scanned / image-only PDFs

**v1: detect and fail clearly; do not OCR.**

Many corpora (including some public-dialogue reports) include scanned or image-heavy PDFs. Shipping OCR in the core path pulls in Tesseract (or similar), adds non-deterministic quality, and expands the test matrix before the text-layer design is stable.

| Capability | v1 | Later |
|------------|----|--------|
| Detect low extractable text (words/page, coverage) | Yes — set `text_layer: absent\|sparse\|present` (or equivalent) on the document / row | — |
| Refuse or empty-segment with an explicit error/warning when strategy requires a text layer | Yes — no silent empty corpus | — |
| Fixture: at least one scan-like / low-text PDF that asserts detection | Yes | — |
| OCR strategy (e.g. `pdf_ocr.v1` via Tesseract or PyMuPDF OCR) | **Out of scope** | Optional reader flag / strategy; extra dependency |
| Manual pre-OCR externally then re-run text-layer path | Supported already (treat as normal PDF) | — |

pub-dialogue’s `ocr_if_image_only` / `MIN_WORDS_PER_PAGE` pattern is the seed for **detection** metrics; the OCR *execution* path stays future work (or stays in the app until a lynguine OCR strategy exists).

### 5. YAML / flow surface (illustrative)

**Path index + access compute** (fits today’s Compute subclass pattern):

```yaml
input:
  type: excel
  filename: data/tech_metadata.xlsx
  index: filename

compute:
  - function: document_segment
    field: [unit_id, text, segment_strategy]
    row_args:
      path: filename
    args:
      reader: pdf
      root: data
      strategy: auto          # or pub_dialogue.v1
      aspect: body_chunks
      min_chunk_words: 40

  - function: extract_references   # optional second aspect
    field: [ref_id, ref_raw]
    row_args:
      path: filename
    args:
      reader: pdf
      root: data
      strategy: auto
```

**Future IO sugar** (only after segment API stabilises):

```yaml
input:
  type: pdf_directory
  source:
    - directory: data
      glob: "*.pdf"
  segment:
    strategy: auto
    aspect: body_chunks
```

v1 should ship **functions + tests**, not rush a new `read_data` type. Directory sugar is a follow-on backlog item.

### 6. Package boundaries and reuse

| Code today | Role under this CIP |
|------------|---------------------|
| `pub_dialogue.access.extract_chunks_from_pdf` | Seed / reference implementation for strategy `pub_dialogue.v1`; eventually call shared segment API or thin-wrap it |
| `dialogue_formats.access.load_corpus` | Seed for `docx_chatbot.v1` / `docx_workshop.v1` strategies |
| referia `pdf_extract_comments` | Stays domain-specific (annotations); not body text |
| CIP-0004 LLM functions | Optional assess-phase on `text` columns |
| CIP-0007 vongole `files.py` | Not a dependency; document→units is lynguine access |

Apps keep research prompts and clustering; lynguine owns the **document → units** contract.

### 7. Out of scope for this CIP (record, do not implement here)

- **lamd talks / snippets** (`talks/_*/*.md`, `snippets/_*/includes/*.md`): already structured markdown + macros. Catalog loading is `markdown_directory` / CIP-000F territory; a future `lamd_talk.v1` slide/notes segmenter is a separate small item, not v1 of this CIP.
- **OCR / scanned PDF text recovery** — see §4.
- **GROBID** as a reference strategy — later optional strategy.
- **Absorbing** pub-dialogue or ai-dialogue-formats into lynguine.

### 8. Testing programme (first-class deliverable)

Treat multi-corpus fixtures as part of the design, not an afterthought.

**Fixture sets** (committed excerpts / redacted pages where licence requires; full PDFs via optional local path):

1. **Public dialogue reports** — sample from pub-dialogue `data/` (varied years; include one low-coverage / scan-like case that asserts **detection**, not OCR success).
2. **PMLR / mlresearch papers** — sample single- and two-column PDFs from `~/mlresearch/v*/` or `assets/` with hand-labelled reference-block start and N reference strings.
3. **DOCX transcripts** — synthetic fixtures already used by ai-dialogue-formats tests (chatbot + workshop shapes).

**Oracle types**:

- Segmentation: expected unit count bands, order-preserving gold snippets, strategy id under `auto`.
- References: gold `ref_raw` list (parsed fields only when explicitly asserted in a later phase).
- Scan detection: fixture asserts `text_layer` / error behaviour without requiring Tesseract in CI.
- Regression: strategy `pub_dialogue.v1` stays within coverage/chunk-stat tolerances from pub-dialogue’s chunking report philosophy.

**Harness**: pytest parametrisation over `tests/fixtures/documents/<corpus>/…` with a small manifest YAML per file (`expected_strategy`, `aspect`, gold files). No API keys and no OCR binary required for access-layer CI.

### 9. Alternatives considered

| Alternative | Why not (for v1) |
|-------------|------------------|
| Single global PDF chunker in `io.py` | Fails the multi-corpus requirement; hides strategy |
| Always LLM-segment | Expensive, non-deterministic, wrong layer for access |
| Wait for vongole | Document→units is access structuring; vongole does not exist yet |
| OCR in core reader | Heavy deps, quality variance; detect-only is enough for honest v1 |
| GROBID-only for references | Strong for some academic PDFs; weak/overkill for dialogue reports |
| Fold lamd talks into v1 | Different problem (macros, not layout recovery) |
| Absorb pub-dialogue / dialogue-formats into lynguine | Violates package boundaries |

### 10. Accepted decisions (was: open questions)

1. **Placement:** lynguine `access.documents` (+ access compute registration). Not blocked on vongole.
2. **Row grain:** explode to unit rows by default; nest optional.
3. **References v1:** `ref_raw` (+ id/order); structured parse later.
4. **`docx_directory`:** keep pandoc path; new structured DOCX path is separate and explicit.
5. **Scanned PDFs:** detect + explicit failure/warning in v1; OCR is future work.

## Implementation Plan

1. **Accepted design** — layering, placement, row grain, references v1, scan policy frozen (this revision).
2. **Document model + PDF reader** — minimal page/block API; wrap PyMuPDF; path confinement via existing `allowed_roots`; expose text-layer stats.
3. **Strategy interface + `pub_dialogue.v1`** — port behaviour from `extract_chunks_from_pdf`; register `document_segment`.
4. **DOCX reader + dialogue strategies** — port/adapt chatbot + workshop unitisation behind strategy ids.
5. **Reference aspect** — region detection + at least one academic prose strategy; fixtures from mlresearch samples.
6. **Recogniser v0** — feature vector + scored ranking; always record choice on output rows; include scan/sparse features.
7. **Testing programme** — fixture manifests, CI without network/OCR, optional local full-corpus path.
8. **App wiring sketches** — example YAML for pub-dialogue metadata→chunks; note dialogue-formats and mlresearch follow-ons.
9. **Later backlog** — `pdf_directory` sugar; OCR strategy; GROBID strategy; CIP-0004-backed reference repair; optional `lamd_talk.v1`.

## Backward Compatibility

- No change to existing `read_data` types until optional directory sugar lands.
- Existing `docx_directory` pandoc behaviour unchanged.
- Apps may adopt `document_segment` incrementally; pub-dialogue / dialogue-formats keep their APIs until they choose to delegate.

## Testing Strategy

See §8. Success for this CIP means the **fixture programme is green in CI** for access/segmentation/references/scan-detection without LLM calls or OCR binaries, plus unit tests for recogniser feature extraction and strategy override.
