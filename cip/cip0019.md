# CIP-0019: Pluggable tabular IO types — `register_io_type` without bloating lynguine

## Summary

Add a tiny, explicit **tabular IO registry** to lynguine so `read_data` / `write_data` can dispatch on `type:` values implemented **outside** the core package. Lynguine keeps builtin file and sheet types. Vendor live stores (Trello, IMAP, Gmail metadata, SQL, …) live in separate packages that call `register_io_type`. referia and other apps only name `type:` in YAML.

This CIP is the **tabular** sibling of [CIP-0013](./cip0013.md). CIP-0013 plugs **document extractors** (`register_strategy`: PDF/DOCX/markdown → units). This CIP plugs **table readers/writers** (`register_io_type`: live store → DataFrame). They share the registry spirit and the “unknown name fails clearly” contract. They do **not** share the document model, and they must not be collapsed into one hook.

**Which requirements does this CIP address?** REQ-0010 (primary). Also REQ-0002 (predictable named types), REQ-0004 (credentials), REQ-0006 (thin lynguine / package boundaries), REQ-0009 (live readers vs `source:` fetch).

## Motivation

Applications already want allocation and input from systems that are not files:

| Wanted input | Grain | Wrong home |
|--------------|-------|------------|
| Trello cards | one row per card | lynguine core, or CIP-0013 strategies |
| Email / Gmail **subjects** (and From/Date/id) | one row per message | referia `type: email` (that is **outbound** drafts) |
| SQL query | one row per result | CIP-0009 `source:` (that is fetch-then-read a file) |
| Google Docs **body** | document units | CIP-0013 (not this CIP) |

Today `read_data` / `write_data` are closed if/elif chains. Unknown `type` raises `Unknown type "{ftype}"`. The only Google live store in core is `gsheet`, which already pulled `gspread-pandas` and `google-api-python-client` in as **hard** dependencies — the cautionary example. Adding Trello, IMAP, and Gmail the same way would bloat lynguine and violate CIP-0007 / REQ-0006 (thin access core).

referia should not grow a parallel IO layer either. Its job is review YAML (`allocation` / `input` / `output`) on top of lynguine access.

Zero-plugin path stays valid: export the board or mailbox to YAML/CSV and use builtins. Plugins exist when the live store is the authoritative input.

## Detailed Description

### Two plug points (do not conflate)

```
CIP-0019 — tabular IO                         CIP-0013 — documents
─────────────────────────                     ────────────────────────────
type: trello | imap | gmail | sql | …         reader: pdf | docx | markdown | …
register_io_type(name, read, write?)          register_strategy / register_engine
details dict → DataFrame                      file → Document → Units → aspect rows
write_data when the type opts in              not a store writer
CIP-0005 credentials for APIs                 path jail / extras (PyMuPDF, …)
```

| Question | CIP-0019 | CIP-0013 |
|----------|----------|----------|
| What is the named thing? | `type:` on an input/output/allocation item | `strategy` / `reader` / `aspect` on document compute (or future directory sugar) |
| What does success look like? | A DataFrame that `finalize_data` can finish | Ordered units with `segment_strategy` recorded |
| Where do plugins live? | Separate packages (`lynguine-trello`, …) | In-tree strategies **or** packaged YAML engines; third-party **document** readers can also live out-of-tree via `register_strategy` |
| Google Docs | No | Yes — a **reader**, then a strategy |
| Gmail **metadata** (subject, from, date, id) | Yes — a table | No |
| Gmail **body** as reviewable text | After metadata IO, treat bytes/path as a document | Yes |
| `pdf_directory` sugar (CIP-0013 §5) | The **dispatch** should use this registry so `io.py` does not grow another elif | The **segment** behaviour stays CIP-0013 |

CIP-0013 v1 correctly deferred a new `read_data` type (`pdf_directory`) until the segment API stabilised. When that sugar lands, register it on **this** hook (core may register builtins the same way plugins register Trello). Do not add a third dispatch style.

### What lynguine adds (small)

Home: `lynguine.access.io` (or a tiny sibling `lynguine.access.io_types` imported by `io.py`). Mirror CIP-0013's `register_strategy` / `get_strategy` / `list_strategies`.

```python
def register_io_type(
    name: str,
    *,
    read: Callable[[dict], pd.DataFrame],
    write: Callable[[pd.DataFrame, dict], None] | None = None,
) -> None:
    """Register a tabular IO type. Replaces any prior entry with the same name."""
```

Dispatch:

1. Look up `details["type"]` in the registry.
2. If present, call `read` / `write`, then existing `finalize_data` (read) or the existing write reshape/omit path (write).
3. If absent, **current** if/elif builtins (v1 may keep builtins as elif and use the registry only for extras). A follow-on can move builtins onto the same registry so there is one dispatch.
4. If still unknown: `ValueError` naming the type and `list_io_types()`, same spirit as `UnknownStrategyError`.

Write: if the type is registered with `write=None`, `write_data` raises a dedicated error (`Type "trello" is read-only`). Do not fall through to a file writer.

`register_io_type` replaces a prior entry with the same name (same as `register_strategy`). Core builtins must not be silently overwritten: attempting to register `csv`, `excel`, … from a plugin raises. Builtin names are an explicit reserved set.

### How a plugin becomes visible (explicit, not magic)

Tenet: no silent “best effort”. Three load paths, all named:

1. **Application import** (always valid): `import lynguine_trello` in the app, which calls `register_io_type` at import. referia (or a notebook) does this once.
2. **Flow `plugins:` list** (recommended for YAML-only configs):

   ```yaml
   plugins:
     - lynguine_trello
   input:
     type: trello
     board: "review-inbox"
     index: id
   ```

   Before `read_data`, the flow imports each module. Failed import names the module and the `type` that needed it. Do not guess extra packages from the type string.

3. **Optional entry points**, loaded **only** when that `type` is requested and not yet registered. Group name `lynguine.io_types`, key = type name. Log the distribution that supplied it. If no entry point exists, the unknown-type error stands — it does not scrape PyPI.

Do **not** auto-import every installed plugin at lynguine import time. That would make `import lynguine` depend on whoever happens to be in the environment.

### Plugin contract

A reader:

- Accepts the same `details` dict other readers see (`type`, `index`, `key`, plus type-specific keys).
- Returns a `pandas.DataFrame` (or object `finalize_data` already accepts).
- Does not call `finalize_data` itself — `read_data` does that, as today.
- Uses CIP-0005 `CredentialManager` for secrets (`details["credential"]` or a type-documented name). No tokens in interface YAML.
- Respects path confinement when it touches the filesystem (REQ-000A). Live HTTP APIs are not files; they still must not treat `filename` as a URL to fetch implicitly (CIP-0009: do not infer download from a URL-shaped name).

A writer (optional):

- Is called after `reshape_for_write` / omit, like builtins.
- Must be **explicitly** enabled in config for dangerous destinations, e.g. `write: true` on the item, so a mis-aimed `output:` cannot mutate Trello. Default is read-only even if `write=` was registered.
- Records enough provenance in logs (type, destination id, row count) without logging credentials.

Type-specific keys stay on the item (`board`, `list`, `mailbox`, `query`). Do not invent a second nested schema that duplicates `type:`.

### Relation to CIP-0009 (`source:`)

CIP-0009 is **fetch a file, then read it** (`source.type: url | github`). Live APIs are **readers**, not fetchers — CIP-0009 already says this for SQL and for `gsheet`.

```yaml
# CIP-0009 — file appears on disk, then type: yaml
input:
  type: yaml
  filename: candidates.yml
  source:
    type: url
    url: https://example.org/candidates.yml

# CIP-0019 — no file; type is the live store
input:
  type: trello
  board: "review-inbox"
  index: id
```

Do not add `source.type: trello`. Do not route Trello through a cache file unless a plugin **chooses** to snapshot (that would be plugin-local, documented, and still `type: trello`).

Gmail/IMAP metadata is `type: imap` (or `gmail`), not `source.type: imap`.

### Relation to CIP-0005

Plugins register **validators** for their credential kinds via the existing `register_validator` API. lynguine does not grow a Trello or Google-mail validator in core unless that credential kind is already there (`google_oauth` is). Prefer reusing `google_oauth` for Gmail/Docs over a second Google secret format.

### Relation to CIP-0007 / CIP-0006

IO plugins are **access**, not vongole assessment compute and not referia review widgets. referia CIP-0006 (referia-first, then promote) still applies to *review-domain* functions. A Trello reader that several apps need should never squat in referia; it should be a lynguine plugin package from the start.

vongole is not a place for `read_data` types.

### Google surfaces (split correctly)

| Surface | CIP | Notes |
|---------|-----|--------|
| Google Sheets | core `type: gsheet` today | Out of scope to extract in v1; *may* later re-register on this hook |
| Gmail message **list** (subject, from, date, id, labels) | **this CIP**, plugin | Tabular allocation/inbox |
| Gmail **body** / MIME parts | CIP-0013 once a path or bytes exist | Document reader, not a table type |
| Google Docs | CIP-0013 | Reader + strategy; not `type: gdocs` as a DataFrame of paragraphs unless exploded as CIP-0013 row grain |
| referia `documents: - type: email` | referia | **Outbound** draft generation; do not reuse for inbound mail |

### Example YAML (illustrative; plugins not in this CIP)

```yaml
plugins:
  - lynguine_trello
  - lynguine_mail

allocation:
  type: trello
  board: "2026-panel"
  list: "To review"
  index: id

input:
  type: imap
  mailbox: INBOX
  fields: [subject, from, date, message_id]
  index: message_id
```

referia keeps using `type: excel` until an operator adds a plugin. No referia code change is required for a new type beyond depending on the plugin package (or listing it under `plugins:`).

### Package sketch (not implemented here)

| Package | `type` | v1 read | v1 write |
|---------|--------|---------|----------|
| `lynguine-trello` | `trello` | cards in a board/list | later; cards/comments |
| `lynguine-mail` | `imap` / `gmail` | message metadata | no |
| (future) `lynguine-sql` | `sql` | query → frame | no (or explicit opt-in) |

Names are illustrative. This CIP ships the **hook and tests**, not those packages.

### Alternatives considered

| Alternative | Why not |
|-------------|---------|
| Add Trello/IMAP elifs to `io.py` | Repeats the gsheet dependency mistake; violates REQ-0006 |
| Reuse CIP-0013 `register_strategy` for Trello | Strategies consume a `Document`; cards are not pages/blocks |
| Reuse CIP-0009 `source.type` | Fetch-then-read a file; live APIs have no local path |
| Auto-discover all entry points at import | Hidden IO in `import lynguine`; environment-dependent |
| Infer type from URL / board id | Implicit infrastructure |
| Implement plugins inside referia | Wrong layer; every app would duplicate |
| Wait for vongole | IO is access, not assessment |
| Make every plugin writable in v1 | Write-back to Trello/mail is easy to get wrong; read-only default |
| Extract `gsheet` in this CIP | Behaviour change for existing flows; separate cleanup |

### Out of scope

- Implementing Trello, IMAP, Gmail, or SQL plugins
- Moving `gsheet` out of core
- CIP-0013 `pdf_directory` sugar itself (only: use this registry when it lands)
- Google Docs reader (CIP-0013)
- Changing referia `type: email` outbound documents
- A plugin marketplace or version negotiation beyond “import this module”

## Implementation Plan

1. **Accept this design** — two registries (IO vs document), reserved builtin names, read-only default, `plugins:` import list.
2. **Registry API** — `register_io_type`, `get_io_type`, `list_io_types`; tests for replace, reserved-name rejection, read-only write error.
3. **Dispatch** — unknown `type` in `read_data` / `write_data` consults the registry before raising; builtin elif path unchanged in v1.
4. **`plugins:` on the interface** — import listed modules during `from_flow` (or immediately before first `read_data`); clear errors.
5. **Optional entry points** — lazy load by type name only; log provider; tested with a fake distribution or `importlib.metadata` stub.
6. **In-tree fake plugin** — e.g. `type: fake_registry` used only in tests (distinct from existing `type: fake` if that would clash — prefer a test-local registration, not a new builtin).
7. **Docs** — short “writing an IO plugin” page: contract, credentials, relation to CIP-0013 and CIP-0009.
8. **Follow-on (not this CIP)** — first real plugin package; optional migration of builtins onto the registry; CIP-0013 directory sugar on the same hook.

## Backward Compatibility

- Existing `type:` values and `source:` blocks unchanged.
- Configs without `plugins:` unchanged.
- Unknown types still raise; error text may additionally list registered plugin types.
- No new required dependencies in lynguine.

## Testing Strategy

- Unit tests for registry (register, list, reserved names, read-only write).
- `read_data` / `write_data` with a function registered in-test (no network).
- `plugins:` import success and failure messages.
- Entry-point lazy load with a stub (optional if the `plugins:` path is tested first; entry points must not be the only load path).
- No Trello/Gmail credentials in CI. No network.
