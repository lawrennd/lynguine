# CIP-0011: Compute phase wiring — document reality, close gaps, restore honest three-phase dispatch

## Summary

Document and then fix the **gap between the documented three-phase compute model** (`precompute` → `compute` → `postcompute`, plus `column_args` / `subseries_args`) and what lynguine and referia v2 actually execute today.

This CIP is **separate** from reshape work ([CIP-0010](./cip0010.md) wide flatten) and from series hardening. Those consumers **depend** on an honest compute stage model; they must not invent parallel “global compute” paths while phases remain unwired. CIP-0007 (lynguine / vongole split) assumes three-phase processing exists in the base engine — this CIP makes that assumption true or revises the contract.

**Which requirements does this CIP address?** REQ-0002 (predictable architecture), REQ-0005 (config flexibility that matches runtime), REQ-0006 (clear access vs assess compute boundaries).

## Motivation

Discussion of CIP-0010 (wide flatten as an access `type` wrapping nested `specifications`) surfaced a sharper problem: callers cannot honestly say “run per-row compute inside the load, then postcompute / column-aware aggregation outside,” because **postcompute is largely declared but not dispatched** on the live paths.

That is not a naming quibble. Docs (`docs/compute_framework.md`), CIP-0007, backlog notes, and referia examples still teach:

```yaml
postcompute:
  - function: sum   # or llm_complete, etc.
    field: total
    column_args:
      values: review_word_count
```

Old referia **did** wire phases. Current lynguine stores the lists, exposes properties, and documents orchestration — but `Compute.run` / `run_all` / access `finalize_data` do not honour the three-phase contract. Referia v2 partially works around this for review UI score hooks by stuffing lists into `interface={"compute": ...}`, which is not the same as top-level `precompute` / `postcompute` keys or old `run_all(pre=, post=)`.

Until this is fixed or the public contract is deliberately narrowed, every design that needs “global” or post-reshape compute (CIP-0010, `read_series`, catalog roots, LLM aggregate examples) is building on sand.

## Detailed Description

### What is wired today (lynguine)

| Surface | Behaviour |
|---------|-----------|
| `Compute.__init__` | Parses interface keys `precompute`, `compute`, `postcompute` into `_computes` |
| Properties `precomputes` / `computes` / `postcomputes` | Return those lists |
| `Compute.run(data, interface)` | Docstring claims three phases; **implementation only walks `interface["compute"]`**. Ignores `_computes["precompute"]` and `_computes["postcompute"]` |
| `Compute.preprocess` | Docstring says precompute; **reads `interface["compute"]` again** |
| `Compute.run_all(data, interface)` | Loops indices and calls `run`; **no pre/post flags**, no phase orchestration |
| `Compute.run_onchange` | Stub (“not yet implemented”) |
| Access `finalize_data` | Thin loop: for each index, call function on `df.loc[ind]`, write `field`. **No `column_args` / `subseries_args` resolution**, no pre/post keys |
| `read_data` → `finalize_data` | Nested `hstack` / `vstack` / `series` (and future `wide_flatten`) get this thin path for nested `compute:` blocks |
| Legacy `lynguine/compute.py` | Older class with `run_all(..., pre=, post=)` that **does** concatenate phase lists — parallel / largely superseded path, easy to confuse with `assess.compute` |

### What old referia did (v1 / pre-migration)

In `old_referia` (and legacy `lynguine/compute.py`):

- `run_all(df=None, index=None, pre=False, post=False)` built  
  `(precompute if pre) + compute + (postcompute if post)`.
- `CustomDataFrame.compute_pre()` / `compute_post()` called `run_all(pre=True)` / `run_all(post=True)`.
- Review UI also had **score-item** types `type: precompute` / `type: postcompute` (display/review), distinct from interface phase keys — collected into reviewer/data lists and run as hooks.

That model is what configs and mental models still expect.

### What referia v2 does today (partial translation)

- Inherits `lynguine.assess.compute.Compute` (`run` / `run_all` without phase flags) — see referia CIP-0001 (test signature migration).
- Still maintains `_precompute` / `_postcompute` lists on data for review score hooks.
- Invokes them via:

  ```python
  self.compute.run(data=self, interface={"compute": self._precompute})
  self.compute.run(data=self, interface={"compute": self._postcompute})
  ```

  So hooks run only because they are **renamed into the `compute` key** for a single `run` call — not because lynguine dispatches phases.
- Examples still show top-level `postcompute:` + `column_args` (e.g. `examples/llm_integration_example.yml`) as if the documented contract worked end-to-end.
- Docs/quickstart still call `compute.run_all(data, interface)` without explaining the lost `pre`/`post` semantics.

### Gaps this causes

1. **False configurability** — YAML `precompute` / `postcompute` appear supported; silent no-op (aside from being stored on the Compute object).
2. **Access vs assess split** — Load-time `finalize_data` cannot express column-aware or post-aggregate ops; assess `run` can resolve `column_args` but only for the `compute` list and typically the focused index.
3. **Migration debt** — Old referia flows that relied on `compute_pre` / `compute_post` or interface phase keys are not faithfully translated; workarounds hide the missing engine behaviour.
4. **Downstream design pressure** — CIP-0010, series, and catalog “one wide row then summarise” designs look forced to invent new stages instead of composing nested access compute + outer postcompute.
5. **Doc / CIP drift** — CIP-0007 and `docs/compute_framework.md` over-claim; tests mostly assert storage or mock `run`, not phase orchestration.

### Related but distinct: `read_series` and CIP-0010

| Capability | Needs from compute CIP |
|------------|-------------------------|
| `read_series` | Clear rule: nested `specifications` get thin finalize compute; list-of-values reshape is access; any column-wide op after series needs assess-phase honesty |
| CIP-0010 wide flatten | Nested multi-row compute before widen; outer single-row (or post) compute after; must not depend on unwired `postcompute` keys until this CIP lands or the contract is narrowed |
| Series save / `entries` | Out of scope here (separate CIP); only note that writable series + onchange currently sit on stub/`run` behaviour |

### Design principles (for the fix)

- **Explicit over magic** — Document the real contract first; then make code match, or delete the keys from the public contract.
- **One dispatch model** — Prefer a single orchestrator used by assess and (optionally) by access finalize, rather than three divergent loops.
- **Preserve access/assess boundary** — Access-level compute may stay thin by policy, but that policy must be documented; do not silently accept `postcompute` on `input:` and ignore it.
- **Migration honesty** — Referia v2 score hooks and old `pre=`/`post=` callers need an explicit compatibility story.

### Decisions to make (acceptance blockers)

These are the open product/architecture choices this CIP must settle before implementation backlog tasks are created:

1. **Phase orchestration API**
   - **A.** Restore old semantics: `run_all(..., pre=, post=)` or `run_phases()` that runs `_computes` lists in order.
   - **B.** Keep `run(data, interface)` but require callers to pass only one phase; add `run_pipeline(data)` that uses stored `_computes`.
   - **C.** Narrow the public contract: remove / deprecate top-level `precompute`/`postcompute` keys; document review hooks as referia-only lists.

2. **Access `finalize_data` vs assess `Compute.run`**
   - **A.** Access stays thin (per-row Series only); document that `column_args` / postcompute are assess-only; nested load `compute:` cannot do aggregates.
   - **B.** Access finalize delegates to assess `Compute` (or shared helper) so nested and outer blocks share one resolver.
   - **C.** Hybrid: thin by default; opt-in `compute_engine: full` on a source.

3. **Where aggregates land**
   - Per focused row (current `set_value_column` style), every row, or a dedicated summary row/frame — must be explicit for `postcompute` + `column_args`.

4. **Referia review hooks vs interface phases**
   - Unify naming (`type: precompute` score items vs interface `precompute:`) or keep two concepts with distinct docs and APIs.

5. **Legacy `lynguine/compute.py`**
   - Delete, merge, or clearly mark dead so phase behaviour cannot fork again.

6. **Ordering relative to CIP-0010**
   - Wide flatten can land as access reshape with thin nested/outer `compute` lists **without** waiting for full postcompute — but docs must not claim postcompute works until this CIP closes (or decision 1C is chosen).

### Proposed direction (straw man for review — not accepted yet)

1. Inventory + truth doc (this CIP’s audit) becomes the normative “as-is” appendix.
2. Implement **decision 1A or 1B**: one pipeline that runs stored `_computes` phases in order; fix `run` docstring; fix `preprocess` to use `precompute`.
3. Choose **2A or 2B** explicitly; if 2A, reject `postcompute` / `column_args` under access details with a clear error.
4. Referia: replace `interface={"compute": self._postcompute}` shims with calls into the real phase API; update examples that show top-level `postcompute`.
5. Add integration tests that fail if `postcompute` is ignored.
6. Update `docs/compute_framework.md` and CIP-0007 references to match.

## Backward Compatibility

- Restoring phase dispatch is **behaviour-changing** for configs that already contain `precompute`/`postcompute` and silently did nothing — treat as bugfix with release note.
- Narrowing the contract (decision 1C) is also breaking for docs/examples; prefer errors over silent ignore.
- Referia score-hook lists should keep working; only the call path changes.

## Testing Strategy

- Unit: phase order, ignore/error policy, `column_args` aggregation writeback.
- Unit: `finalize_data` thin vs full per decision 2.
- Integration: nested `yaml_directory` + compute + (future) `wide_flatten` + outer compute; assert no reliance on unwired keys.
- Migration: golden test from an old_referia-style `pre`/`post` sequence against the new API.
- Negative: document that current tests mocking `run` are insufficient; replace with behavioural asserts.
