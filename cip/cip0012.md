## Summary

Audit how lynguine exposes and uses **`pivot` / `pivot_table`** (and related reshape APIs), document the contract relative to [CIP-0010](./cip0010.md) wide flatten/unflatten and view-style indexing, and decide whether any API, docs, or write-path changes are warranted.

This CIP is a **review first**; implementation tasks are created only after Accept and after the audit concludes what (if anything) should change.

**Decision (2026-10-11):** inventory and CIP-0010 / store-views work show that **heavy pivot work is not worth doing now**. Prefer a **docs-only** close: keep the thin wrapper, document “lossy; not for editable scores; prefer tall store + views.” Reopen only if a real flow starts editing through a pivot.

**Which requirements does this CIP address?** REQ-0002 (predictable behaviour), REQ-0005 (config flexibility where reshape is exposed), REQ-0006 (reshape policy stays in infrastructure, not ad-hoc application code).

## Motivation

[CIP-0010](./cip0010.md) established that wide reshape and pivot are cousins: lossless wide forms need an explicit inverse (or a **view** that never replaces the tall store); aggregating `pivot_table` is lossy and must not pretend to round-trip.

Today lynguine has a thin `CustomDataFrame.pivot_table` wrapper and no first-class YAML/access pivot step, no documented invertibility policy, and no write-path unpivot. Before anyone builds editable or persisted flows on pivot-shaped data, the project should **review** current usage, gaps, and whether CIP-0010’s Pattern A (tall store + virtual wide access via `get_value` / `set_value`) should be the shared model for pivot-like views too.

## Detailed Description

### What to review

1. **API surface** — `CustomDataFrame.pivot_table` (and any `pivot` / `stack` / `unstack` exposure); callers in lynguine tests and referia.
2. **Semantics** — When aggregation is used vs a lossless reshape; whether defaults encourage lossy tables.
3. **Persistence** — Interaction with `write_data` / scores: does anything assume a pivoted frame is written as-is?
4. **Relation to CIP-0010** — Shared vocabulary: materialized wide vs **view over tall** (index + column focus); when `wide_unflatten` is needed vs name→`(index, field)` resolution on get/set.
5. **Relation to CIP-0011** — If pivot were ever a flow/compute step, phase wiring must be honest.
6. **Docs** — README / assess docs: what users are told today vs what is true.

### Audit findings (2026-10-11)

| Finding | Evidence |
|---------|----------|
| **API** | Thin `CustomDataFrame.pivot_table` → `pandas.DataFrame.pivot_table`; no `pivot` / `stack` / `unstack` first-class exposure |
| **YAML / access** | No `type: pivot` (or similar) flow step — unlike `wide_flatten`, nothing in access config to confuse with `columns` / finalize |
| **Callers** | One characterisation test in `lynguine/tests/test_assess_data.py`; **no** referia (or other app) production usage found |
| **Policy already settled** | [Authoritative Store and Views](../tenets/lynguine/authoritative-store-and-views.md) + CIP-0010 Pattern A: aggregating pivots are lossy presentation, not the editable store |
| **Cross-docs** | CIP-0010 and README already point catalog authors away from aggregating `pivot_table` for `complete` / editable scores |

### Decision

**Not worth building** as an implementation CIP right now:

- No API split (`pivot` vs `pivot_table`)
- No shared pivot view helper beyond what CIP-0010 already provides for wide names
- No write-path unpivot

**Worth at most docs-only:**

- Short note on `CustomDataFrame.pivot_table` docstring and/or README: lossy; not for scores; prefer tall store + views (Pattern A)
- Then **Close** this CIP (or treat remaining docstring as a tiny backlog item under docs-only)

**Reopen** (or Accept a follow-on) only if a real flow starts editing or persisting through a pivot-shaped frame.

### Likely outcomes (post-audit)

| Outcome | Status |
|---------|--------|
| **Docs-only** | **Chosen** — wrapper is fine; document “lossy; not for editable scores; prefer tall store + view” |
| **API tighten** | Deferred — no demand |
| **Shared view helper** | Covered by CIP-0010 Pattern A for wide-like access; no separate pivot helper needed yet |
| **Write unpivot** | Deferred — no supported flow materializes pivoted editable data |
| **No heavy code change** | **Confirmed** — audit finds no production use; keep thin wrapper |

### Out of scope (unless a future reopen forces a follow-on)

- Implementing catalog/events UI (referia CIP-0010).
- Replacing CIP-0010’s `wide_flatten` with pivot.
- Series / `entries` hardening.
- Pivot write-path / YAML pivot type without a concrete caller.

## Implementation Plan

1. **Inventory** — Grep/tests/docs for pivot usage; summarise in this CIP. **Done (2026-10-11).**
2. **Contract draft** — Tall store vs materialized pivot; get/set view vs reshape; write policy. **Settled by store/views tenet + CIP-0010;** no separate pivot contract needed beyond docs.
3. **Decision** — Docs-only; no Accept → heavy backlog. Optional: docstring/README note, then Close.
4. **Cross-links** — CIP-0010 / README already reference this CIP; after Close, keep pointer or note “docs-only; no write unpivot.”

## Backward Compatibility

Review itself is non-breaking. Docs-only changes must not alter `pivot_table` wrapper behaviour. Any future API change must preserve or deprecate the existing wrapper explicitly.

## Testing Strategy

- Existing characterisation test for `pivot_table` is sufficient while the wrapper stays thin.
- If a future reopen adds implementation: round-trip tests only for **lossless** paths; aggregating paths assert non-invertibility / documented errors.
