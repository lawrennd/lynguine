## Summary

Add an explicit **lynguine** reshape that turns a multi-row DataFrame into a **single row** whose column names incorporate the former index values (pandas-style `unstack` + flat MultiIndex names). No parent index is required — unlike lynguine/referia **series** nesting.

This is **not** the referia catalog/events CIP. Hex numbers are per-repository: **lynguine CIP-0010** = this wide-flatten reshape; **referia CIP-0010** (separate repo) = config-driven catalog / events root that consumes CIP-000F directory rows (and may optionally call this reshape). Series hardening remains a further CIP in whichever repo owns that work. Nested vs outer `compute` composition depends on honest phase dispatch — see [CIP-0011](./cip0011.md); do not assume top-level `postcompute` works until that CIP lands or narrows the contract.

**Which requirements does this CIP address?** REQ-0002 (predictable, explicit flow), REQ-0005 (configuration flexibility), REQ-0006 (reshape stays in infrastructure; applications do not invent ad-hoc wide pivots), REQ-000C (singleton / composed frames use wrapping `index` — tall key nested; no `result_index` synonym).

**Downstream:** a referia catalog or document flow may opt into this reshape when a directory of configs should appear as **one data point** (browser-style listing via Liquid + `flattenKeys`). Writable progress (`complete`) stays on the **tall** store; wide names resolve via get/set (Pattern A). Materialized `wide_unflatten` is secondary. Pivot policy is [CIP-0012](./cip0012.md).

**Tenet:** [Authoritative Store and Views](../tenets/lynguine/authoritative-store-and-views.md) (Proposed) — access may materialize snapshots; edit/Save stay on the store; wide names are views unless the flow explicitly chooses Pattern B.

## Motivation

Directory allocation (including CIP-000F recursive `yaml_directory` + field projection) correctly produces **one row per file**. Some UIs and documents want the opposite presentation: **one data point** whose fields are the discovered rows, with names that still identify which source each value came from.

Today lynguine has related but different operations:

| Capability | Shape | Parent index? |
|------------|--------|----------------|
| `read_series` | one row; values are **lists** per column | yes (grouped by index) |
| referia series → `entries` | one parent row; nested list-of-dicts | yes |
| `stack` / `hstack` / `vstack` | concatenate **sources** | n/a |
| `CustomDataFrame.pivot_table` | thin pandas wrapper, not a YAML flow step | varies |

None of these implement: **N rows × M columns → 1 row × (N×M) columns**, with names like `{index}{sep}{field}`.

Pandas does this with `unstack` (index → column level) then flattening MultiIndex names (there is no `DataFrame.flatten()`). Lynguine should expose that reshape as an **explicit, documented** flow/assess step so callers do not copy SO one-liners into application code.

## Detailed Description

### Design principles

- **Explicit over magic.** Opt-in config (or named assess op). Default allocation behaviour unchanged.
- **No parent index required.** Unlike series, the result is a solitary wide row (or a trivial single-index frame), not children under a parent key.
- **Names from the index.** Former index values must appear in the new column names (or as a MultiIndex level that is then flattened for Liquid/Excel).
- **Infrastructure stays generic.** No knowledge of `_referia.yml` or catalog UX.
- **Separate from series.** Series (list nesting / writable subseries) needs its own tests and review CIP; this CIP does not harden series save paths.

### Pandas baseline

Idiomatic reshape:

```python
wide = df.unstack().to_frame().T
wide.columns = wide.columns.map(lambda x: separator.join(map(str, x)))
```

Column order depends on MultiIndex level order and optional `sort_index`. Document the chosen default (`index_then_field` vs `field_then_index`) and keep it configurable.

### Accepted API placement

**Access `type: wide_flatten`**, same composition model as `series` / `hstack` / `vstack`:

- Nested `specifications` loaded via `read_data` (so nested `compute:` runs through `finalize_data` on the multi-row frame).
- Outer reshape to one wide row; outer `compute:` on the `wide_flatten` details runs via the outer `finalize_data`.
- Not a compute-registry function and not assess-only: callers need nested vs outer compute choice at load time.
- Config key / type name is **`wide_flatten`** (not bare `flatten` or `unstack`) to avoid pandas/`stack` confusion.
- Full `postcompute` / `column_args` honesty remains [CIP-0011](./cip0011.md); v1 of this CIP only relies on the thin per-row `compute` lists that `finalize_data` already runs.

### Configuration sketch

```yaml
input:
  type: wide_flatten
  separator: "_"
  order: index_then_field   # or field_then_index
  index: root               # singleton label of the wide result (REQ-000C)
  columns:                  # optional: subset of fields to widen
    - title
    - date
    - complete
  specifications:
    type: yaml_directory
    # tall identity before flatten: column / index on nested source
    # (e.g. set_index via nested index key or compute that yields configPath)
    # ... CIP-000F-style multi-row source ...
    compute:                # optional: runs on N rows (finalize_data)
      - field: ...
  compute:                  # optional: runs on the single wide row
    - field: ...
```

Result for tall index values `grant/a`, `grant/b` and fields `title`, `complete` (wide row itself indexed `root`):

| grant/a_title | grant/a_complete | grant/b_title | grant/b_complete |
|---------------|------------------|---------------|------------------|
| A             | true             | B             | false            |

### Edge cases (must specify in tests)

- Non-unique index → clear error (cannot unstack unambiguously).
- Empty frame → one empty row or empty columns; pick and document.
- Index values that contain the separator → document escaping or forbid; prefer documenting “separator must not appear in index strings” for v1 unless a safe escape is cheap.
- Non-string index / column names → `str(...)` in the join.
- Optional column subset leaves other columns dropped or kept as globals — document.

### Loop keys on the wide row (required for Liquid listings)

Wide columns alone are not enough to recreate a directory-style `{% for %}`. Directory allocation already attaches path metadata per row (`store_fields`: `sourceDirectory`, `sourceFile`, …). After flatten those become wide scalars *if* listed in `columns`, but the **ordered list of former index labels** must also be a first-class field on the wide row (e.g. `flattenKeys`), not recovered by splitting column names in the application.

v1 shipped without this; **in scope for this CIP** before Closed:

- Emit `flattenKeys` (name configurable) as a list column on the single wide row — the index values used for name prefixes, in stable order.
- Document that Liquid/templates loop `flattenKeys` and resolve `{key}{sep}{field}` (or a small helper filter later).
- Keep path fields (`sourceDirectory`, …) as widened value columns when the caller includes them; do not force the filesystem path to *be* the index if the separator policy would break (prefer a safe key + path as a field).

### Writable assessments (`complete`): view over tall, not reshape the store

`write_data` writes the DataFrame **as shaped in memory**. If the authoritative `CustomDataFrame` were replaced by a materialized wide row, Save would persist wide columns unless something unflattens first.

**Preferred Pattern A — tall store + virtual wide view (no shape change on get/set):**

- Join discovery + scores stay **tall** (stable key = config path/key). That tall frame remains what `get_value` / `set_value` and `write_data` use.
- “Wide flatten as a view” means: expose `flattenKeys` plus name resolution so a logical field `"{key}{sep}{field}"` maps to **set index → `key`, column → `field`**, then existing get/set. The pandas representation does **not** become one wide row for editing.
- Liquid/address may still ask for a **materialized** wide snapshot (flat dict for templates); that snapshot is read-only presentation unless an explicit write-back path is defined.
- Save always writes **tall** scores — no unflatten step in the common path.

**Pattern B — materialized wide as the in-memory/output shape** (discouraged for catalogs):

- `wide_flatten` replaces (or becomes) the working frame including `complete`.
- Then either persist wide (schema grows with keys) or **`wide_unflatten`** before tall `write_data`.

**Recommendation for catalog `complete`:** Pattern **A** with **indexing**, not reshape-on-write. Widgets and filters that speak wide names go through the resolver into the tall store. Do not wide_flatten the scores DataFrame just to edit `complete`.

### Materialized inverse (`wide_unflatten`) — still in scope, narrower role

Keep `wide_unflatten` for:

- Round-trip / tests of the access `type: wide_flatten` helper.
- Pattern B or any flow that **materialized** a wide frame and must write tall.
- Building or validating Liquid snapshots that were edited as a wide dict (if we ever support that).

Not required on every Save under Pattern A if get/set never left tall storage.

### Relation to pivot tables

| | `wide_flatten` / `unstack` | `pivot` / `pivot_table` |
|--|---------------------------|-------------------------|
| Typical use | Every former row becomes a block of columns | Values spread by a *column* of categories; often **aggregated** |
| Invertible? | **Yes**, if index unique and names parse cleanly (`stack`/`melt`) | **Only** if no aggregation (`pivot`); `pivot_table` with `sum`/`mean` is **lossy** |
| Preferred editable model | Tall store + virtual name→`(index, field)` view | Same idea if a “pivot view” is ever editable; do not replace the store with an aggregating table |

Pivot **code and write-path policy** are reviewed in **[CIP-0012](./cip0012.md)** (Proposed). This CIP only records the analogy and points catalog authors away from aggregating `pivot_table` for `complete`.

### Out of scope

- Referia series → `entries` nesting and writable series Excel save behaviour (separate CIP).
- Catalog UI filters / Liquid chrome (**referia** CIP-0010 — different document/repo).
- Changing CIP-000F discovery semantics.
- Pivot / `pivot_table` API review and any pivot write-path work — **[CIP-0012](./cip0012.md)**.

### Alternatives considered

1. **Series / `entries` without a real parent** — forces a fake parent index; wrong topology for “root is the only point.”
2. **`read_series` lists** — keeps column names but loses per-source scalar fields; poor for templates that want `{{grant_a_title}}`-style names.
3. **Application-side pandas** — works once; violates explicit infrastructure and duplicates policy/tests.
4. **True MultiIndex columns only** — elegant in pandas; awkward for Liquid and Excel mapping. Prefer flatten-to-strings as the default export shape; MultiIndex may be an internal step.
5. **Wide scores on disk without unflatten** — schema churn as the tree grows; rejected as default for catalogs.

## Implementation Plan

1. **Phase 1 (done)** — `wide_flatten_dataframe` + `type: wide_flatten` access + tests + docs.
2. **Phase 2a** — Emit `flattenKeys` (configurable name); document safe index vs `sourceDirectory` fields.
3. **Phase 2b** — Virtual wide view: name→`(index, field)` resolution for get/set over the **tall** store (primary Pattern A path).
4. **Phase 2c** — `wide_unflatten_dataframe` for materialized round-trip / Pattern B; tests; document A vs B. Pivot review lives in CIP-0012.
5. **Phase 3 (Accepted 2026-10-11 — REQ-000C)** — Align wrapping `index` with `stack` / `local`: outer `index` = singleton **result** label; tall pre-flatten identity on nested `specifications` (or tall frame index). No `result_index`. Legacy: omit outer `index` → keep today’s `0`; document deprecation for new configs.

## Backward Compatibility

Additive only. Existing flows unchanged until they opt into `flatten` (or equivalent). No change to `stack` / `hstack` / `vstack` / `read_series` semantics.

## Testing Strategy

- Pure unit tests on a small fixture DataFrame (no filesystem).
- One integration-style test: multi-row `yaml_directory` (or in-memory frame from CIP-000F-style projection) → flatten → assert column set and single-row values.
- **`flattenKeys`** present, ordered, matches index used for prefixes.
- **View path:** resolve `"{key}{sep}{field}"` → get/set on tall frame without changing `df.shape`.
- **Materialized round-trip:** `wide_unflatten(wide_flatten(df[columns]))` recovers tall frame; errors on ambiguous parse / separator policy.
- Optional: widget-style edit via resolver updates tall `complete`; `write_data` sees tall columns only.

## Accepted amend (Phase 3 — REQ-000C)

**Accepted 2026-10-11.** Survey of referia configs: wrapping `index` is ubiquitous; `result_index` was never used in the wild. Align `wide_flatten` with `stack` / `local`:

| Key | Meaning after amend |
|-----|---------------------|
| Outer `index` | Label of the **single wide row** (required for new explicit configs; omit → legacy `0`) |
| Nested tall identity | Column/`index` on `specifications` (or index already set on the nested frame) used for flatten prefixes / `flattenKeys` |

**Breaking note:** Today outer `index` means “tall column to `set_index` before flatten.” After Phase 3 that meaning moves nested. Document migration in README; update tests that pass outer `index` as a column name.
